# Windows MVP 验证

在 Windows 10 和 11 x64 的独立快照中使用普通账号执行。
使用可回滚的测试快照和专门的第三方测试安装项。
不要用生产电脑和自己的真实应用数据验证卸载、隔离及还原。

## 自动检查

```console
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo run -p uninstallany-windows --example inventory --locked
```

枚举示例不启动卸载器，也不改变应用或注册表项。它可以写入工具自己的本地审计目录。
对照「已安装的应用」及实际来源核对同名但不同范围的条目、32/64 位视图、包应用和系统组件。
预装包、框架包、受保护的发行商项或无法识别为应用的包可能出现在不可卸载的范围。

Windows 原生写入夹具放在单独标记的 ignored 测试中。仅在可回滚的专用 VM 执行。

```powershell
$env:UNINSTALLANY_DISPOSABLE_WINDOWS_VM = '1'
cargo test -p uninstallany-windows --locked -- --ignored --nocapture
```

## 手动冒烟顺序

1. 建立快照，安装一个 MSI、一个支持静默卸载的 Win32 EXE 和一个当前用户 MSIX 样本。
   选用严格应用名作为安装目录的 Win32 样本，另备同发行商双应用和安装位置重叠的对照项。
   记录测试程序的文件和注册表分布，分辨每个应用的专属项、共享项、保留数据。
2. 启动桌面端，核对应用列表，再输入一个已知便携测试目录的绝对路径。
   按[便携应用目录](#便携应用目录)核对候选的证据、置信度和风险，以及确认前保持原样的文件和注册表。
3. 在桌面端选择测试应用，预览官方卸载方式与范围，再确认并检查执行结果。
   核对 Win32 quiet 和 interactive 选择、MSI 的 ProductCode、MSIX 的完整包身份。
   在确认前用同一测试登记切换 `NoRemove`，核对桌面端重新读取卸载资格并拒绝启动原生卸载。
   用一个只写标记的 Win32 测试卸载器预览。保持预览框打开，从同一账号修改登记中当前使用的 `QuietUninstallString` 或 `UninstallString`，只修改参数，保留原 EXE 和其他元数据。
   确认原预览，核对两个版本的标记都未写入，应用登记和安装目录仍存在，并且没有自动生成残留清单。
   恢复登记并重新预览，再创建不同键名的第二个测试应用登记，使其 `InstallLocation` 指向同一个目录。
   确认原预览，核对独占目录复核拒绝启动卸载器。
   两次反例完成后撤销测试登记的改动，再从新预览执行成功路径。
   对异步安装器、无法确定子进程完成、取消、非零返回码或待重启状态，检查报告及自动扫描边界。
   Windows 取消等待的验收见[取消等待 Windows 卸载](#取消等待-windows-卸载)。
   同一用户的双实例和桌面端关闭后的验收见[跨实例写入保护](#跨实例写入保护)。
   当前用户 Startup 文件夹的验收见[当前用户 Startup 快捷方式](#当前用户-startup-快捷方式)。
   普通 Win32 和 MSI 快捷方式的验收见[卸载前记录的改名快捷方式](#卸载前记录的改名快捷方式)。
   普通桌面应用的用户数据残留见[当前用户 AppData 残留](#当前用户-appdata-残留)。
   MSIX 残留的验收见[MSIX 快捷方式和包数据](#msix-快捷方式和包数据)。
   缺少安装位置的 Win32 样本见[缺少 InstallLocation 的 Win32 卸载](#缺少-installlocation-的-win32-卸载)。
4. 在清单只勾选本次测试残留，审阅确认框后执行。
   同卷单文件应进入隔离槽。目录和未经核实的高风险项应保留。
   安装位置只能证明根目录的归属，子文件缺少独立证据时不会默认勾选。
   对 HKCU 软件键单值，先确认 `.reg` 和原始类型备份已经写入，复核同键其它值及另一个视图。
   应用重新出现时的验收步骤见[卸载后重新出现](#卸载后重新出现)。
5. 在隔离区选择这批备份，审阅还原清单并确认。
   复核文件内容和原对象、注册表视图和值类型及内容。
   用新文件或新注册表值占用原位置，复测确认不会覆盖。
6. 复测锁定文件、访问拒绝、不同卷、用户重定向目录、同名安装目录和中间 symlink／junction。
   再测试末端链接时，单独记录链接及目标身份，任何隔离动作只可移动链接对象。
   检查其它应用和保护目录下的标记均存在。
7. 在隔离完成或注册表事务提交后、写入回执前模拟进程中断。
   重启后核对隔离身份和审计状态。文件可通过同一隔离槽核对是否已移动。
   无法确定是否已提交的注册表备份必须保留并提示复核。
   文件还原的中断边界见[文件还原中断](#文件还原中断)。
   注册表事务的中断验收见[注册表提交后的中断恢复](#注册表提交后的中断恢复)。
8. 按[操作日志导出](#操作日志导出)从设置页导出本次记录，核对目标路径、权限和防覆盖行为。

普通用户实例拒绝以提升后的令牌启动。
卸载准备和执行前按原始应用 ID 复核。注册表项限定当前用户或登记的机器视图，MSIX 限定当前用户和完整包名。
桌面应用启动卸载程序前会重新读取该登记及卸载命令。Win32 还会用最新登记列表重新核对安装目录是否独占。
登记变更、Win32 目录归属无法核实或发现重叠时，需要重新预览。
目录归属的复核规则与测试见 [ARP 目录归属](#arp-目录归属)。
当前审查范围是无需提权的精确操作，强制移除的 ARP 整键在缺少完整安全描述符时显示为只读。
文件隔离以同卷 NTFS 为限。已经启动的厂商卸载程序由系统及厂商负责。
普通目录保持只读。NTFS 重命名接口没有「源目录必须为空」的原子条件，其他进程可在枚举结束后创建子项。
目录 oplock 对子项变化只提供通知，子项写入无需等待确认。 [微软 FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) · [微软目录 oplock](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_request_oplock#remarks)
服务、计划任务、防火墙规则、文件关联、COM 和 Shell 扩展以高风险只读候选显示。
扫描以应用独占安装目录与本地 EXE 或 DLL 的直接引用作为归属依据。
计划任务仅覆盖单个直接执行动作。文件关联覆盖同一注册表来源中的默认 ProgID，Shell 扩展覆盖右键菜单和属性页处理程序。
官方卸载完成并核实原卸载登记已消失后，指向旧安装目录内缺失文件的登记可作为中置信度只读线索。
旧目录须与应用名严格匹配，且当前没有其他应用登记使用该目录。
缺失必须由可访问的本地文件系统确认。链接、路径别名、共享范围和读取失败均无法作为缺失证据。
执行已批准的清理时，仍重新核对可写目标的归属、风险和原生身份。

## 便携应用目录

在 Windows 桌面端提交一个专属便携应用目录的绝对路径（`scan_portable`）。
扫描使用现有清理预览和确认流程，限制在所选目录内，检查系统和共享范围、链接、重解析点及 ARP 安装归属。
Windows 桌面端的已安装应用残留由官方卸载后自动扫描，或由下文的强制移除入口产生。

1. 在本地 NTFS 卷准备一个未登记、无归属冲突的专属测试目录，放入两个普通文件，并在同级目录放一个对照文件。
   输入展开后的绝对路径并预览，检查候选局限于测试目录，文件和注册表原样保留，且没有该计划产生的隔离槽内容或清理回执。
   只确认一个测试文件，核对它进入隔离区，另两个文件保留，再确认还原并核对内容。
2. 分别提交相对路径、带 `..` 的路径、盘符根、受保护的系统或用户目录根、共享范围、作为目录入口的 junction 或符号链接，以及中间经过重解析点的路径。
   核对各例均无法取得可执行清理计划，链接目标和其中的标记保持原位。
   用一个已安装应用的目录再复测，并按 [ARP 目录归属](#arp-目录归属)在正常预览后引入指向测试目录的登记。
   确认旧预览，核对重叠目录中的文件保持原位。

## 强制移除

在 Windows 桌面端对准确选中的第三方 Win32 登记打开「预览强制移除」（`scan_force_removal`）。
资格要求原始 ARP 登记可完整核实且不受系统或安装器管理，并满足以下任一条件。

- `UninstallString` 和 `QuietUninstallString` 原始值均不存在。
- 至少有一条卸载命令，且每条现存命令均直接指向独立核实的专属安装目录内的字面、本地 EXE，所有这些 EXE 均已确认缺失。
- 本次会话中 Windows Job 已确认卸载器及受跟踪子进程结束并失败，失败结果已写入审计，且距记录未满 15 分钟。复核时须匹配原登记、卸载 EXE、使用过的图标 EXE 及相应目录证据。

取消、待重启、观察不完整或进程仍在运行的结果无法作为失败证据。
空值、畸形命令、MSI、MSIX、受保护登记及 `NoRemove` 样本均无法取得强制移除权限。
清理预览绑定原始 ARP 键的指纹，确认复扫时重新核实资格，并在移动目标文件或打开注册表写事务前复核该指纹。
若原 ARP 键可写且用户选中它，则在其余选中项之后处理。
普通权限下只有完整安全描述符和所需访问权限均可核实时，ARP 整键才可写。
整键只读时，已获准的独立残留仍按各自的隔离及备份流程处理。
符合条件的 Win32 登记可以列出指向其专属安装目录的当前用户 Startup 链接，验收见[当前用户 Startup 快捷方式](#当前用户-startup-快捷方式)。

1. 用独立快照分别准备两个登记样本。一个省略两条命令，另一个保留两条直接指向独占安装目录内确实不存在的 EXE 的字面命令。
   分别打开预览，核对风险提示和候选归属。确认前两个样本的文件及登记原样保留，且没有清理备份或成功回执。
   在第二个样本的独立快照中，取得预览后恢复其中一个 EXE，确认旧预览，核对文件和登记保留且未产生清理成功回执。
   再用空字符串、错误值类型、非直接命令、目录外 EXE 或登记归属不明的版本复测，核对无可执行计划。
2. 让非 MSI 的无害测试卸载器及受跟踪子进程退出，根进程返回测试失败码 `7`，并保留原 EXE、登记和残留标记。
   核对审计中的卸载失败记录，同会话内取得强制移除预览，再分别复测重启桌面端、超过 15 分钟、替换 EXE 或其证据所依赖的图标 EXE。
   核对这些反例无法使用该失败记录。另用取消、待重启、进程未结束、受保护、`NoRemove`、MSI 和 MSIX 对照，核对均无法靠失败结果取得清理权限。
3. 分别在打开预览后改写登记值，以及删除后在原位置重建该测试登记，再确认旧预览。
   在独立快照中于文件移动或注册表事务之前的逐项复核处暂停，重建测试登记再继续。
   核对原计划拒绝变更受影响项，标记仍在原位置，登记及对照值保持现状，且无清理成功回执。
4. 从原始夹具重新预览，只勾选已核实的残留；如整键显示为可写，可同时勾选原 ARP 键。
   核对文件进入隔离区，可写注册表项先有 `.reg` 和原始类型快照，选中的原 ARP 键最后处理。
   如整键为只读，核对清理报告没有删除该键。用同一批次确认还原，核对应用文件、登记值的内容和类型以及无关项。

## 当前用户启动注册值

当前用户的 `Run` 和 `RunOnce` 可在明确确认后清理单个值。
候选须为无参数的直接本地 EXE，程序须仍位于该应用的已核实安装目录内。
预览、确认后复扫和删除前都核对注册表值，以及 EXE 的文件身份和内容指纹。
删除前写入 `.reg` 与私有快照。
还原时核对原值未被占用，并验证同一个 EXE 的身份和内容。
同一批次还原时先回放文件，再恢复启动值。 [Microsoft Run 和 RunOnce 说明](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)

1. 让无害的 Win32 测试卸载器仅移除自身卸载登记，保留专属目录中的 EXE 及指向它的一个当前用户启动值。
   分别使用 `Run` 和 `RunOnce` 复测，并在同一注册表键下保留一个无关的对照值。
   在同一次登录会话内完成 `RunOnce` 验证，以免 Windows 在登录时消费该值。
2. 打开残留预览，保持注册表值不变，将原 EXE 暂时改名，再放入另一份同名的无害 EXE。
   确认旧预览，核对该项被跳过，原启动值及对照值保持原样，且该项没有生成 `.reg`、私有快照或清理成功回执。
3. 从初始快照重做测试卸载，在新预览中仅确认清理测试启动值。
   核对 `.reg` 和私有快照已保存，只移除了该值，对照值的类型与内容保持原样。
   在还原预览后用同样方式替换 EXE，核对还原被拒绝、启动值仍不存在，且备份可用。
   把原 EXE 移回原名后重新预览还原，核对测试值的名称、类型和内容恢复，对照值保持原样。

## 当前用户 Startup 快捷方式

Windows 登录时可运行当前用户或所有用户 Startup 文件夹内的快捷方式。
两类文件夹的当前和默认路径均纳入通用清理与还原的保护范围，涵盖 Windows 返回的路径及其规范化位置。 [Microsoft 启动应用说明](https://support.microsoft.com/en-us/windows/experience/startup-boot/configure-startup-applications-in-windows) · [Microsoft 已知文件夹标识](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)
专用流程仅处理当前用户的 `FOLDERID_Startup` 与默认位置一致时的目录直放 `.lnk`，且该目录须是当前用户默认 `FOLDERID_Programs` 的直接子目录。
快捷方式须为普通文件，`LinkInfo` 须直接指向固定本地卷上的字面 EXE 路径。
含替代目标、参数、工作目录、附加数据块或文件系统别名的链接无法通过核验。 [Microsoft Shell Link 标志](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/ae350202-3ba9-4790-9e9e-98935f4ee5af)

启动 Win32 官方卸载器前，后端记录合格 `.lnk` 的内容指纹和目标 EXE 的原生文件身份与内容指纹。
目标须位于应用在 ARP 卸载登记中声明、且已核实为该应用专属的安装目录内。
官方卸载结果核实后，只有原链接未变且原 EXE 仍存在、身份和内容均一致时，才会生成「启动项」精确匹配候选。

[强制移除](#强制移除)只为符合资格的 Win32 应用生成这类候选。
目标须为该应用原始 ARP 登记明确声明的独占 `InstallLocation` 内仍存在的、以字面路径记录的原生 EXE。
推断的安装目录、已缺失的 EXE、安装归属不明或与 ARP 路径声明重叠的快捷方式均无法取得写入资格。
预览与确认复扫比对链接的原生身份、内容指纹及目标 EXE 的原生身份与内容指纹。
写入逐项备份意图后，移动每个强制移除链接前再读取 ARP 登记，复核强制移除资格与安装目录及链接的独占归属。
注册表复核与文件句柄固定是独立步骤，外部进程可在最后一次注册表读取后新增或修改登记。

候选为高风险，默认不勾选。
隔离与还原均持有已复核的目标 EXE 句柄直至移动完成，还原拒绝覆盖原位置上的现有文件。
同一批次内，如链接和目标 EXE 均可独立清理，隔离先处理依赖链接，还原先处理普通文件中的 EXE。
这项操作保持 `StartupApproved` 登记原样。

1. 用只移除自身 ARP 登记的测试卸载器，保留专属安装目录中的原 EXE 和默认 Startup 下的一份合格 `.lnk`。
   另放一份指向其他应用的对照链接，记录链接内容和现有 `StartupApproved` 值。
   确认官方卸载后，核对残留预览只允许手动勾选已核实的链接，确认清理前文件保持原位。
   只隔离该链接，再还原并核对链接的原始内容。对照链接和 `StartupApproved` 始终保持原样。
2. 用独立快照让卸载器移除目标 EXE，或在卸载后用不同 EXE 占用原路径。
   在另一个快照中先取得正常预览，再分别替换目标 EXE、改写或替换 `.lnk`，然后确认旧预览。
   核对缺失及变更的目标无法清理，现有文件保持原位。
   用含参数、工作目录、替代目标或附加数据块的链接，以及目标使用路径别名的链接复测，核对均无法执行清理。
3. 在只隔离了链接的快照中，分别用其他文件占用原 `.lnk` 路径，或在还原预览后替换、改写目标 EXE。
   核对还原被拒绝且隔离备份仍可用，现有文件保持原样。
   另选一个目标 EXE 本身也满足清理条件的夹具，同时勾选链接和 EXE。
   按操作日志核对隔离顺序为链接、EXE，还原顺序为 EXE、链接。
4. 用独立快照分别重定向当前用户或公共 Startup，在当前和默认位置放置对照链接。
   核对一般扫描无法将这些路径纳入可写清单，专用流程也不会清理重定向的当前用户 Startup 或公共 Startup。
   另在重定向前隔离一个合格的旧桌面 `.lnk`，随后把当前用户 Startup 指向该链接的原父目录。
   尝试还原旧备份，核对目标位置保持原样，备份仍在隔离区。
5. 在独立快照中准备一个符合强制移除条件的 Win32 测试登记，明确设置专属 `InstallLocation`，并在默认 Startup 放置指向该目录内现有测试 EXE 的 `.lnk`。
   同时放入指向其他应用的对照链接，打开强制移除预览，核对仅自己的链接可手动勾选且默认不勾选。
   单独确认隔离已核实链接后还原，核对链接的原始内容以及对照链接的位置和内容。
   若链接、目标 EXE 和原 ARP 键均可写，另做一次混合选择，核对隔离先移动链接，再处理 EXE，原 ARP 键最后处理。还原时核对 EXE 先于链接。
6. 用独立快照先打开强制移除预览，再分别改写或替换 `.lnk`、替换其目标 EXE，然后确认旧预览。
   核对受影响的链接保持原位，清理报告没有该项的成功回执。
7. 使用卸载 EXE 已缺失的样本，在强制移除预览后分别新增与安装目录重叠的 ARP 路径声明、新增与链接重叠的 ARP 路径声明，或恢复缺失的卸载 EXE。
   分别在确认前和逐项备份意图已写入、最后一次 ARP 复核尚未开始时引入每种变更。
   核对原计划阻止链接移动，链接保持原位，清理报告没有该项的成功回执。
8. 用共享或重定向的 Startup、受保护的 Startup 路径、未声明 `InstallLocation` 或目标 EXE 缺失的样本复测强制移除。
   核对这些链接均未进入可写清单。

## 取消等待 Windows 卸载

普通 Win32 卸载对主进程使用 100 毫秒的有界等待，收到取消信号后再做一次零等待检查。
跟踪子进程时，先读取 Job 的活动进程数，再决定是否停止等待。
若已观察到进程结束，保留实际退出结果并按原流程核实卸载结果。
若取消时进程仍在运行，或主进程返回零后子进程等待超时，记录「无法确认完成」。
若主进程已返回非零退出码，保留该原生结果，同时继续观察仍活跃的子进程。
无法读取观察状态时也会保留句柄，当前项不进入残留清理。[Microsoft WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)

桌面端保留进程和 Job 的观察句柄，关窗后的延续行为见[跨实例写入保护](#跨实例写入保护)。
仍有受观察进程运行时，可以刷新应用列表，新的卸载、清理、到期清除和还原请求会被拒绝。
这些请求将在复核确认进程退出后恢复。
Job 未启用关闭即终止的限制，释放观察句柄不会终止厂商进程。[Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

Win32 和直接 MSI 在 `CreateProcessW` 前复查取消信号，MSIX 在 `RemovePackageAsync` 前复查。
提权助手在请求 UAC 和发送卸载请求前分别复查。
直接 MSI、MSIX 已启动或助手请求已经发出后，桌面端继续等待系统或助手的原生结果。
如果等待或通信失败且未取得结束证据，易失启动登记会继续阻止后续写入。

1. 使用有启动标记和手动放行条件的无害 Win32 卸载夹具。
   一次让主进程停在放行点，另一次让主进程返回零并只留下同一 Job 内的受控子进程。
   各自在夹具停住且等待未超时时点取消，核对结果为「无法确认完成」，厂商进程保持运行，没有残留清理预览，队列下一项未写入启动标记。
2. 在夹具仍停住时刷新应用列表，并尝试预览另一个卸载或残留清理任务。
   对已有的测试备份再尝试确认还原及到期清除，核对应用列表可读，相关操作均未写入。
   放行夹具并确认受观察进程均已退出，核对新预览的操作可以继续。
3. 用能移除自身卸载登记的测试夹具复测进程先结束的边界。
   在读取最终结果前触发取消，核对已完成结果仍显示「已完成」，残留扫描和后续队列项停止。
   再使用返回「需要重启」结果的 MSI 样本，在其原生操作期间取消，核对仍报告「需要重启」，队列后续项未启动。
4. 让夹具的主进程返回零，保留一个超过 30 秒的同 Job 子进程，并保持等待。
   核对报告提示观察超时、没有残留预览，后续队列项的启动标记未写入。
   再让主进程返回错误码且留下子进程，确认报告保留原错误码，并在子进程退出前暂停后续写入。

## 跨实例写入保护

同一 Windows 用户的卸载、隔离、还原和到期清除共享对私有文件 `Coordination\mutation.lock` 的独占占用。
后端从确认时的重新检查起持有该文件，直至原生写入及结果审计完成。
打开协调目录和占用文件时核对所有者、访问权限及路径身份，拒绝跟随链接或使用多重硬链接文件。
应用清单和已有备份清单仍可读取。

桌面端在当前用户的注册表配置单元（hive）内用同一个易失键 `HKCU\Software\UninstallAny.PendingWin32Launch` 登记原生卸载。
普通 Win32 仍在调用 `CreateProcessW` 前创建启动意图。
只有原生调用确认已创建进程后，才将意图标为已提交。
Job 使用随机名称，其他实例只能在登记已提交、能打开对应 Job 且活动进程数为零时确认其结束。
最后一个用户态句柄释放后，临时 Job 的名称可能已消失，而成员进程仍可运行。 [微软内核对象生命周期](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/life-cycle-of-an-object#temporary-and-permanent-objects) · [微软内核对象命名空间](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces)

取消等待后正常关闭窗口，原桌面进程在 Tauri 退出后继续以同一用户保留句柄，仅观察尚未结束的 Win32 卸载。
关闭窗口和释放观察句柄均不会终止厂商进程。
若观察进程被强制结束或启动提交中断，且新实例无法取得完成证据，写入保持阻断。
仅受 Job 跟踪的普通 Win32 卸载支持关窗后继续观察。 [微软 Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

### 系统卸载的启动登记

三种系统卸载在下表所列边界之前写入各自的待结束状态。
发出原生请求和清除登记均在持有文件锁时进行。

| 路径 | 写入登记的时机 | 可解除登记的结束证据 |
| --- | --- | --- |
| 直接 MSI | 桌面端调用 `CreateProcessW` 启动 `msiexec.exe` 前 | 已持有的主进程句柄已触发，并成功读出可确认结束的原始退出码。 |
| 提权 MSI | 助手身份及本地管道核验完成后，桌面端首次发送已获授权的卸载请求前 | 从已验证的同一助手连接收到有效且可确认结束的 `Outcome` 回复。 |
| 当前用户 MSIX | 桌面端调用 `RemovePackageAsync` 前 | 同一个异步操作的状态为 `Completed`、`Error` 或 `Canceled`。 |

Windows 的原生进程终止和异步结果由各自接口报告。 [微软 CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) · [微软 GetExitCodeProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess) · [微软 RemovePackageAsync](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.removepackageasync) · [微软 WinRT 异步状态](https://learn.microsoft.com/en-us/uwp/api/windows.foundation.iasyncinfo.status)

已登记的请求若能证明从未发出，例如边界前取消或直接 MSI 确认未创建进程，也可清除登记。
助手发送失败、超时、断连、无效响应或 `Rejected`，以及已经调用 `RemovePackageAsync` 后的调用错误或状态读取失败，均不能证明系统工作已结束。
观察直接 MSI 主进程或读取其退出码失败也保留登记。
这些情况报告「无法确认完成」，不触发残留扫描或 MSI 提权重试。
原生结束证据允许解除登记，卸载成功还须通过独立的安装状态核验。
如果解除登记失败，报告会保留已观察到的原生结果并提示写入仍可能受阻。

### MSI 退出码与待重启状态

直接 MSI 和提权助手按完整的 32 位原始退出码判定结果。
安装已暂停的 `1604` 和无法确认结束的原始码（包括 `259`、`1726`、带高位的异常码或 HRESULT）保留启动登记，并报告 `Unverified` 和原始码。
即使 HRESULT 的低位等于拒绝访问或需要提权，这类结果仍阻止发出提权重试。
`1641` 和 `3010` 均报告 `NeedsRestart` 并保留启动登记，直接使用 `/norestart` 的便携卸载路径也适用。
`1602` 报告取消，`1603` 和安装程序忙的 `1618` 报告失败。三者均解除本次登记，`1618` 由用户在相关操作结束后重新发起。
若原生退出码确认为 `0`，但产品状态核验失败，结果是 `Unverified(0)`，本次启动登记仍可解除。
以上未核实成功的结果阻止自动残留扫描。[微软 Windows Installer 退出码](https://learn.microsoft.com/en-us/windows/win32/msi/error-codes) · [微软 Win32 系统错误码](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1700-3999-)

新版提权助手用 `Unsettled` 回复待重启或无法确认结束的结果。
已支持启动登记但无法解析 `Unsettled` 的旧版桌面端会保留登记。
新版桌面端收到旧助手的 `Outcome` 回复时，会将其中的 `Failed(1604)` 或未知失败码转换为 `Unverified`，并继续保留 `NeedsRestart` 的启动登记。

MSI 的结束证据只覆盖 Windows Installer 本身。安装包可把厂商 EXE 自定义动作为 `Async + Continue`，这类进程可能在 Installer 退出后继续执行。[微软 MSI 自定义动作返回选项](https://learn.microsoft.com/en-us/windows/win32/msi/custom-action-return-processing-options)

### 启动登记失效边界

旧版识别同一键上的 Win32 状态 `0` 和 `1`，遇到新增的系统状态 `2` 至 `4` 会拒绝写入。
只要当前用户的 hive 仍加载，桌面进程崩溃或被强制结束后，其他实例仍会看到登记并阻止新的写入。
Windows 重启或注销时可能卸载用户 hive，使待结束登记消失。[微软易失注册表键](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeyexw) · [微软注销时的用户注册表策略](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-userprofiles#dontforceunloadhive)
重启后 Windows Installer 可能继续或回滚已暂停的操作。应单独核实其结果，再对该应用发起新预览。[微软 MSI 重启说明](https://learn.microsoft.com/en-us/windows/win32/msi/system-reboots)

### Windows VM 验收

1. 在普通用户 VM 启动两个桌面实例，准备可还原的测试备份和一项可清理的无害标记文件。
   让实例 A 的 Win32 夹具运行至受控等待点，同时在实例 B 刷新应用和备份清单，再确认从 A 启动前就已取得的清理或还原预览。
   核对清单仍可读取，实例 B 的变更被阻止，所有测试标记、隔离内容、注册表值及清理回执保持原状。
   在独立快照中于实例 A 写入目标后、保存结果审计前暂停，复测实例 B 的变更仍被阻止。
2. 让夹具主进程退出，仅保留同一 Job 内等待放行的测试子进程。
   在实例 A 取消等待后关闭窗口，核对原桌面进程仍在观察，测试子进程仍在运行。
   打开新实例，核对应用可枚举，卸载及清理写入受阻。
   放行子进程并等待其自行退出，再用新实例取得预览并确认测试操作，核对写入恢复，原观察进程正常退出。
3. 从独立快照重复关窗步骤，在子进程仍停住时仅强制结束经 PID 核实的原桌面观察进程。
   保留夹具子进程，重开界面，核对即使它随后自行退出，丢失观察证据的实例仍拒绝写入，目标保持原样。
   再于 `CreateProcessW` 成功返回与登记提交之间模拟桌面端中断，复测未提交的意图同样阻止写入。
   使用 Windows 的「重新启动」，再通过新预览确认无害操作恢复。
4. 在独立快照中把 `Coordination` 目录替换为指向专用对照位置的 junction。
   再分别把 `mutation.lock` 替换为符号链接、硬链接或普通用户无权打开的对照文件。
   核对新写入被拒绝，未改写占用文件所指向的对象及对照标记，应用清单仍可读取。
   另在独立快照中保留应用的启动登记键但移除其 `Launch` 值，核对无法将不完整登记当作空闲。
5. 分别用直接 MSI、经核实部署助手的机器级 MSI 和当前用户 MSIX 样本，在原生请求已发出但未收到结束证据时暂停实例 A。
   用实例 B 刷新清单，并尝试确认已取得的无害清理预览，核对读取可用、写入受阻。
   在独立快照中只强制结束经 PID 核实的桌面进程，保持同一用户登录，再用新实例复测，核对登记仍在、后续写入受阻。
   如有仅支持 Win32 状态的旧版，用同一用户复测，核对旧版也无法开始新写入。
   使用 Windows 的「重新启动」，单独核查该次部署的安装状态。确认部署结束后，核对独立测试目标可从新预览继续。
6. 在快照内模拟助手请求可能已送达却出现管道断开、超时、无效回复或 `Rejected` 的情况。
   分别模拟直接 MSI 等待或读取退出码失败，以及 MSIX 调用错误或操作状态不可读。
   核对结果为「无法确认完成」，无残留预览，后续卸载未发出，MSI 未产生新的 UAC 提示或助手请求。
7. 对提权 MSI 拒绝 UAC，并在另一快照中于助手发送请求前取消。
   对直接 MSI 和 MSIX 分别在写入登记后、调用原生接口前取消。
   核对未发生卸载，登记缺失或已清除，新确认的无害写入可继续。
8. 用独立快照分别核对 MSI 返回 `0`、`1602`、`1603`、`1618`。
   核对本次登记清除，界面保留对应的成功、取消或失败结果，`1618` 不自动重试。
   在 `0` 的独立夹具中分别保留产品登记及模拟产品状态查询失败，核对结果为 `Unverified(0)`，登记仍清除且残留预览不可用。
   对 MSIX 模拟已看到终态但读取结果失败，核对仍报告「无法确认完成」，且可在没有其他保护条件时确认新的无害写入。
9. 在独立快照中，让受控直接 MSI 夹具及提权助手分别报告 `1604`、`259`、`1726`、带高位的异常码以及 `0x80070005`。
   核对结果为 `Unverified`，诊断保留完整原始码，启动登记继续阻止写入，且无残留扫描、UAC 或助手重试。
   再分别模拟 `1641` 和 `3010`，包括直接 `/norestart` 路径，核对报告 `NeedsRestart`，登记保留并阻止后续写入及残留扫描。
   从真实暂停的 MSI 夹具复测时，重启后先观察 Windows Installer 是否继续或回滚，再核对当前产品状态。
10. 在受控夹具中，用已支持启动登记的旧版桌面端分别接收新版助手的待重启和未核实结果，核对读不到 `Unsettled` 时仍保留登记。
    用新版桌面端接收旧助手的 `Outcome(Failed(1604))`、`Outcome(Failed(1726))` 和 `Outcome(NeedsRestart)`，核对前两项报告 `Unverified`、最后一项仍提示重启，三项都阻止写入和残留扫描。

## 操作日志导出

在 Windows 桌面端的「设置 → 操作日志」输入本地固定 NTFS 卷上一个新 `.jsonl` 文件的绝对路径，点击「导出日志」。
导出逐级打开并持有目录句柄，全程不跟随重解析点。
后端在已核实的父目录下创建暂存文件，并通过句柄发布到该目录下的空闲名称。
暂存和发布后的文件使用当前用户与 `SYSTEM` 专用的受保护 ACL。
取消或可处理错误通过暂存文件的原句柄清理未发布内容。
如果暂存文件清理失败，错误包含该暂存文件名。
每行是一条 JSON 记录，结果字段保留结构化状态或原生数字错误码，旧记录中的原始诊断文本省略。
应用名称、对象路径及备份路径仍是报告的一部分。 [微软句柄相对重命名](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) · [微软文件安全描述符](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)

1. 在专用 VM 中用无害测试样本产生卸载和隔离记录，再导出到当前用户测试目录。
   核对显示条数与文件行数一致，每行均可独立解析，并验证 ACL 的允许项仅为当前用户和 `SYSTEM`。
   核对样本应用名和对象路径仍可见；使用包含专用测试文本的历史诊断夹具时，确认原文未出现在导出的结果字段。
2. 分别使用已有普通文件和指向不存在对象的符号链接作为最终 `.jsonl` 路径。
   核对导出被拒绝，已有文件内容、链接及链接目标状态均保持原样。
   再尝试相对路径、非 `.jsonl` 路径、文件流、网络路径、非固定或非 NTFS 盘、经过 junction 的路径，以及系统目录、共享用户配置文件和工具自己的私有存储目录。
   核对失败位置没有报告或暂存文件。
3. 在专用快照中暂停于暂存文件创建后、发布前，发出取消后继续。
   核对最终路径仍空闲，且本次暂存文件已清理。
   在独立快照中于同一位置创建同名对照文件，继续后核对导出拒绝覆盖，暂存文件已清理，对照内容保持原样。
4. 使用两个普通测试目录，先选择第一个目录导出，然后在持有父目录句柄时从另一进程尝试改名，并在原路径放置指向第二个目录的 junction。
   核对目录替换受阻，或地址复核阻止发布。允许成功的报告只能落在原先核实的目录，第二个目录中的对照文件保持原样。

## 当前用户 AppData 残留

Win32 或 MSI 桌面应用的官方卸载已核实成功后，可预览当前用户 AppData 中卸载前已经存在的残留文件。
候选目录须直接位于当前用户的 `FOLDERID_LocalAppData` 或 `FOLDERID_RoamingAppData` 下，且根目录须与 Windows 默认位置一致。 [Microsoft 已知文件夹标识](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)

候选目录名须与应用的字面显示名严格匹配。
受保护、共享、系统内置或通用目录名，以及与卸载登记路径证据重叠的目录，均无法进入此清理范围。
归属核验要求卸载登记读取完整，并能排除归一化名称相同的其他应用或发行商声明。

每个候选目录最多检查 512 个条目，包含候选目录本身，向下最多检查三层。
只纳入当前用户 AppData 目录内可核实的普通文件，跳过重解析点、快捷方式及受管理或离线条目。
初次预览和确认复扫都将叶文件身份、完整祖先目录身份和原生元数据与卸载前的记录核对。
候选为中置信度、高风险，默认不勾选。
确认后逐个将所选文件移入隔离区，普通还原流程可将文件移回原处并防止覆盖。

1. 在普通用户 VM 中准备一个 Win32 样本及一个 MSI 样本，分别用独立快照完成验收。
   在默认 Local 和 Roaming AppData 中分别创建与测试应用显示名严格相同的直属目录，并放入普通文件和不超过三层的嵌套文件。
   在同级的相似但不同名目录中放置一份对照文件。
   让官方卸载保留测试文件，核对 AppData 清单只包含已核实的文件，且这些候选默认不勾选。
   手动选中一个文件，核对其隔离记录、原位置及对照文件，再确认还原并核对内容。
2. 在独立快照中让卸载器改写一个已记录文件并新增一个文件。
   核对这两个文件无法按本流程清理。
   另在打开清单后、确认前，分别改写候选文件或在原路径换入另一个目录并将原文件移入。
   核对旧清单无法隔离更改过的文件或原目录身份已变化的文件。
3. 分别添加与选定应用的名称或发行商冲突的测试登记，以及指向候选目录或其子路径的测试登记。
   在另一快照中模拟一条测试登记无法读取。
   分别在卸载前和生成清单后引入这些条件，核对它们会阻止相应项取得有效的清理授权。
4. 在快照中分别使用重定向后的 AppData、指向其他目录的 junction 或符号链接、快捷方式、受管理或离线条目，以及放在另一用户配置文件中的对照文件。
   核对无关目标、链接和这些测试对象均保持原样。
   另外放入深度超过三层的文件及总数超过 512 的条目，核对超出扫描范围的项目无法清理。

## App Paths 默认值

只有在官方卸载结果已核实后，才可清理原生视图下 `HKCU\Software\Microsoft\Windows\CurrentVersion\App Paths\应用.exe` 的 `(Default)` 值。
该键须只有默认值且没有子键，机器范围的 App Paths 中也须没有同名键。
默认值须以字面 `REG_SZ` 指向旧独占安装目录中仍存在的同名本地 EXE，目标路径须经过规范化核验。
预览、确认复核、删除和还原都核对同一个 EXE 的原生文件身份及内容指纹。[Microsoft App Paths 应用注册说明](https://learn.microsoft.com/en-us/windows/win32/shell/app-registration#using-the-app-paths-subkey)

该项为高风险，默认不勾选。
删除前先保存 `.reg` 与私有类型快照，再通过注册表事务仅移除默认值，保留键及其权限。
同时确认默认值和 EXE 时，先清理默认值，再隔离 EXE。
还原顺序相反，只有原键仍存在、为空且类与权限匹配，同时 EXE 身份和内容符合备份，才能写回默认值。

1. 在普通用户 VM 中准备一个专属目录内的无害 Win32 样本。
   让测试卸载器只写启动标记和移除自己的卸载登记，保留原 EXE。
   在 HKCU 原生 App Paths 下为该 EXE 建立同名键，仅写入默认值，内容为该 EXE 的绝对路径。
2. 执行官方卸载并确认 App Paths 的默认值可勾选且默认不勾选。
   手动勾选该值和对应 EXE，确认 `.reg` 仅包含默认值 `@=`，审计顺序为默认值清理在前、EXE 隔离在后。
   核对原键和权限保留，再还原同一批次，检查先恢复 EXE，随后按原类型恢复默认值。
3. 在独立快照中复测存在其他值或子键、只有 HKLM 条目或存在同名 HKLM 条目、键名与 EXE 名不同，以及 EXE 缺失。
   确认这些登记无法勾选清理。
   再分别于预览后替换默认值或 EXE，检查旧预览无法删除该值。
4. 另做一批仅清理默认值的操作，保留 EXE。
   在还原前分别占用原默认值、为原键加入其他值或子键、删除原键，或用不同文件替换该 EXE。
   核对 App Paths 还原被拒绝，现有内容保持原样。

## 失效快捷方式

当前用户桌面和扫描已覆盖的开始菜单位置中的 `.lnk`，在目标路径与卷标识都能核实后，可经确认移入隔离区。[Microsoft Shell Link 格式](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/6813269d-0cc8-4be2-933f-e96e8e3412dc)

已有的名称匹配流程可在已核实的 Win32 官方卸载后列出当前用户已知快捷方式目录内的普通 `.lnk`，其名称须与应用严格匹配。
直接目标须是旧独占安装目录内确认缺失的本地 EXE，且快捷方式记录的卷序列号须和最后一个通过句柄核实的祖先目录一致。
候选为中置信度、高风险，默认不勾选。
路径或目标有歧义、存在启动参数、卷不符或位置共享的快捷方式保持只读或不进入清单。
确认后复查目标证据，隔离和还原时继续校验快捷方式内容的 SHA-256 指纹。[Microsoft Shell Link 卷标识](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/b7b3eea7-dbff-4275-bd58-83ba3f12d87a)

1. 在当前用户桌面放置一个与应用同名的直接 `.lnk` 测试夹具。
   夹具目标只记录本地固定卷和安装目录内的绝对 EXE 路径，省略备用目标、追踪数据和启动参数。
   将链接的工作目录设为安装目录，让此用例单独覆盖严格名称匹配流程。
   使用桌面或扫描已覆盖的其他当前用户已知快捷方式位置完成验收。
2. 用官方方式卸载应用，确认目标 EXE 已移除且 `.lnk` 仍在。
   核对残留清单的置信度、风险和默认勾选状态。
   只手动勾选该快捷方式并确认，检查隔离区回执，再还原到原位置并核对文件内容。
3. 各用独立快照分别复测预览后让目标 EXE 重新出现、替换或改写 `.lnk`。
   确认原预览，核对旧计划拒绝移动快捷方式，文件仍在原位置。
   另用卷序列号不符、含备用目标或处于共享目录的夹具复测，确认这些条目无法勾选。

## 卸载前记录的改名快捷方式

普通 Win32 或 MSI 应用调用官方卸载前，后端可记录其用户已经改名的普通 `.lnk`，在核实卸载成功后按原文件证据识别残留。
范围限于当前用户未经重定向的默认桌面直放文件，以及当前用户默认本地 Programs 根和最多两层子目录内的链接。
范围排除 Startup、Windows 工具和管理工具、公共位置以及共享路径。[Microsoft 已知文件夹标识](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)

链接须直接记录原安装目录内固定本地卷上的字面 EXE 路径，原安装目录须由卸载登记明确声明并核实为独占。
目标须为原生 PE 可执行文件、只有一个硬链接，且可在本地完整读取。
含备用目标、命令行参数、工作目录、快捷键或附加数据块的链接不具备此流程的资格。[Microsoft Shell Link 标志](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/ae350202-3ba9-4790-9e9e-98935f4ee5af) · [Microsoft Shell Link 卷标识](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/b7b3eea7-dbff-4275-bd58-83ba3f12d87a)
卸载前保留链接的精确路径、原生文件身份、完整祖先身份和内容指纹，以及目标 EXE 的身份链和内容指纹。
一次发现最多检查 5,000 个目录条目，最多为目标 EXE 内容核验累计预留 256 MiB，失败的读取也消耗这项预算。
达到上限时，只有已取得完整证据的链接可能进入这条清理流程。

卸载成功后生成残留预览和确认复扫时，链接的原路径、身份链及内容须与卸载前证据相同。
EXE 须在原卷上确认缺失，仍存在的原 EXE 祖先目录须逐一匹配其原生身份。
卸载前、预览、确认复扫和移动前均检查 ARP 归属，其他安装记录对链接或目标路径的声明、链接名与其他应用冲突，以及无法核实归属时均阻止清理。
候选显示为高置信度、高风险，默认不勾选。
写入备份意图后，移动前再次核实链接和目标，持有仍存在的最近目标祖先及其上级目录句柄至隔离移动结束。
这些句柄阻止已打开目录被替换，外部进程仍可能在最后一次核验后创建同名目标。[Microsoft 文件共享和删除访问](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
还原沿用普通链接隔离的内容和原位置核验，拒绝覆盖现有文件。它只还原原链接，目标 EXE 的存在与否不影响这一步，也不会执行链接。

1. 在独立快照中分别使用 Win32 和 MSI 夹具，将指向其专属目录内原生 EXE 的合格 `.lnk` 在卸载前改成与应用无关的名称。
   分别在默认桌面直放、默认 Programs 直放和两层 Programs 子目录中放置链接，并保留指向另一应用的对照链接。
   官方卸载删除原 EXE 并保留链接后，核对只有归属可证实的链接成为高风险且默认不勾选的候选。
2. 在独立快照中于卸载前证据已记录后分别改名、改写或替换 `.lnk`，再完成官方卸载。
   另在取得正常残留预览后重复这些变更，再确认旧预览。
   核对受影响的链接无法按旧证据移入隔离区，现有文件保持原位。
3. 分别在卸载后保留改写过的目标 EXE、在确认前恢复原 EXE 或放入不同 EXE。
   再分别替换目标的中间目录但仍让 EXE 缺失，以及撤销普通用户读取目标路径所需权限。
   核对旧计划拒绝移动链接。用独立快照在备份意图写入后、移动前复核前恢复目标 EXE，再次核对拒绝结果。
4. 在候选目录中分别放置带有参数、工作目录、快捷键、备用目标或扩展数据的夹具，并放置同类链接作为公共桌面、公共 Programs、Windows 工具、Startup 和 Programs 第三层的对照。
   分别在开始扫描前和取得预览后重新配置桌面或 Programs，另复测将根目录替换为 junction。
   核对不符合当前范围的链接无法按此流程清理，当前位置和目标均保持原样。
5. 用独立快照在启动官方卸载前、残留预览前、确认前和逐项移动前的复核点引入 ARP 对照登记。
   分别让该登记声明同一链接、同一目标或登记与链接同名的另一应用。
   再复测 ARP 读取不完整，核对这些情况均保留链接，且没有该项的成功回执。
6. 只隔离一个合格链接，保持原 EXE 缺失，再用对照文件占用链接原位置。
   核对还原被拒绝，隔离备份仍可用，随后移走对照文件并重新确认还原，核对原始链接字节和还原位置。
7. 用受控夹具分别超过目录条目上限和 EXE 内容核验字节预算，核对没有卸载前完整证据的改名链接仍在原位置。

## 默认开始菜单 Programs

扫描范围使用当前用户的 `FOLDERID_Programs`。
该位置须与 Windows 默认位置一致，处于当前用户配置文件内，并位于漫游 AppData 的 `Microsoft` 目录及当前 `FOLDERID_StartMenu` 下。
名称匹配的 Win32 扫描支持根目录直放的普通 `.lnk`，也支持经过最多两层与应用名或发行商名严格匹配的子目录。
卸载前按目标身份发现的链接见[卸载前记录的改名快捷方式](#卸载前记录的改名快捷方式)。
一般 Programs 扫描排除系统已知的 Startup、Windows 工具或管理工具，以及公共 Programs 的当前和默认位置。
符合条件的默认 Startup 直放 `.lnk` 走[当前用户 Startup 快捷方式](#当前用户-startup-快捷方式)的专用流程。
重定向的 Programs 根或含链接和重解析点的根路径无法取得此扫描范围。[Microsoft 已知文件夹标识](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)

1. 在使用默认 Programs 路径的普通用户 VM 中，准备同一个测试应用的直接 `.lnk` 夹具。
   分别放在 `Programs\应用.lnk`、`Programs\应用\应用.lnk` 和 `Programs\发行商\应用\应用.lnk`，目录及文件名使用样本登记中的名称。
   按[失效快捷方式](#失效快捷方式)设置工作目录并卸载目标，核对名称匹配路径只出现一次，且中置信度、高风险、默认不勾选。
   手动勾选并隔离其中一项，再确认能够无覆盖还原。
2. 为同样的失效快捷方式放置同名反例，分别使用三层子目录、同级无关目录、Startup、Windows 工具和公共 Programs。
   在应用子目录放置同名普通文本文件，并用另一个匹配名称的目录联接指向扫描范围外。
   核对一般 Programs 扫描不会将反例列为可勾选项，并确认隔离合格项后，同级目录和联接目标的标记文件保持原样。
3. 在独立快照中，通过同一用户的已知文件夹配置将 Programs 重定向到另一位置，再复测扫描。
   另用替换为目录联接的 Programs 根复测，确认目标目录中的夹具保持原位。
   对正常范围仍复测修改 `.lnk` 或恢复目标 EXE 后再确认旧清单，核对复核拒绝移动。

## MSIX 快捷方式和包数据

授权官方卸载时，当前用户的完整包名必须与 Windows 返回的规范标识严格一致。
核对卸载结果时，在当前用户的同一包族内按序号规则忽略大小写比较完整包名，仍区分版本和架构。
任何同族版本仍有当前用户登记，或在确认前重新登记时，均拒绝执行残留清理。 [微软包身份](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/package-identity-overview) · [按用户和包族查询](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.findpackagesforuser) · [CompareStringOrdinal](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-comparestringordinal)

应用名或发行商名称命中的外部对象只作为只读线索。
当前用户的 `%LOCALAPPDATA%\Packages\<包族>` 只检查该确切目录是否存在，目录受保护且不会遍历其中内容。
Windows 可以在移除用户登记后继续保留由其他用户、依赖或预配状态引用的暂存包。 [微软 MSIX 包生命周期](https://learn.microsoft.com/en-us/windows/msix/package/package-lifetime)

卸载前从 WinRT 应用列表读取 AUMID，由 Shell 取得并核实它是当前用户 AppsFolder 的直接子项，再记录其 PIDL。
扫描当前用户本地桌面的直接子项，以及本地默认 Start Menu Programs 中最多两层子目录里的普通 `.lnk`，合计最多检查 5,000 个条目。
快捷方式字节经不跟随链接的文件句柄读取，仅用离线解析器提取目标 ID 列表，并与可信 PIDL 完整逐字节比对。
带有本地路径、备用目标、启动参数、提权标志、无法判断的命名空间目标或额外数据块的快捷方式无法取得写入资格。
只有卸载前已经记录且卸载后仍是同一 NTFS 对象、内容指纹一致的链接，才可能作为高风险候选出现，默认不勾选。
隔离和还原按同卷槽位及禁止覆盖的规则执行。
覆盖范围取决于当前 Windows Shell 能否返回与普通 `.lnk` 内目标列表完全相同的 PIDL。 [微软 AUMID 属性](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.core.applistentry.appusermodelid?view=winrt-28000) · [AppsFolder PIDL](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderidlist) · [Shell Link 目标列表](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/881d7a83-07a5-4702-93e3-f9fc34c3e1e4)

1. 在普通用户 VM 中安装两款显示名称相同、包族不同的无害测试 MSIX。
   两个包都已安装后，为各自的 AppsFolder 应用准备一个目标列表可核实的普通 `.lnk`，放在当前用户桌面或默认 Programs 子目录。
   另在可扫描的外部位置放置同名普通文件，并记录两个包的完整标识、AUMID 及各文件的内容。

   若原包的确切快捷方式由 Windows 留下且通过 PIDL 比对，核对它为高风险且默认不勾选。
2. 手动确认隔离该快捷方式，核对原位置空闲及隔离槽记录。
   用无害对照文件占用原位置，确认还原会保留对照文件和隔离对象。
   移走对照文件并重新确认还原，核对原位置的快捷方式内容与隔离前一致。
3. 用独立快照复测同名不同 PIDL、含额外属性数据或备用目标的 `.lnk`，并放置一份同样目标的副本于桌面下的子目录或共享 Programs。
   核对这些条目无法勾选。另复测在卸载前采集完成后才创建匹配目标的链接，或用同名副本替换已经预览的链接。
   核对新创建、替换或改写的链接保持原位，旧计划没有该项成功回执。
4. 使用同包族的 v1 和 v2，得到 v1 的快捷方式残留预览后安装或注册 v2，再确认原计划。
   核对 v1 仍可报告已卸载，但链接保持原位。对于支持两版本同时登记的样本，保留另一个版本复测，核对同样无法清理。
   在独立快照中，用当前包完整包名的大小写变体核对原生存在性比较，并验证该变体无法替代规范 ID 授权卸载。

   核对目录内文件没有进入可执行清单，共享数据和另一包的目录保持原样。

## 卸载后重新出现

核实官方卸载成功要求原生操作成功，且原卸载登记或原 MSIX 完整包名已经消失。
生成残留预览、确认后复扫及每项写入前，分别复核原 ARP 键或当前用户的 MSIX 包家族是否重新出现。
文件在写入隔离意图后、移动前复核，注册表在打开写事务前复核。
不同键的 ARP 登记与旧目录的重叠由复扫识别，复扫之后仍有并发窗口。
MSIX 完整包名包含版本和架构，家族名称由包名称和发行者确定。[Microsoft 包身份说明](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/package-identity-overview) · [按用户和包家族查询](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.findpackagesforuser)

MSI 还须用原卸载命令绑定的 ProductCode 同时核对机器级、当前用户托管和当前用户非托管三个安装上下文。
三次查询均返回 `ERROR_UNKNOWN_PRODUCT` 才通过，即使原 ARP 键已经消失，产品已安装、已公告或查询失败仍会阻止残留清理。
这项核验由发起请求的桌面进程在自身令牌下完成，也适用于使用其他管理员账户运行提权助手的成功结果。
首次扫描前、确认复扫时，以及每个文件或注册表项的备份意图写入后、实际变更前，均复核同一个 ProductCode。[Microsoft MSI 产品状态查询](https://learn.microsoft.com/en-us/windows/win32/api/msi/nf-msi-msigetproductinfoexw)

1. 在同一 VM 用户下准备两个已签名的可卸载 MSIX，保持包家族相同，版本和完整包名不同。
   安装 v1，并按[MSIX 快捷方式和包数据](#msix-快捷方式和包数据)准备可核实的普通 `.lnk`。
   卸载 v1，获得该快捷方式的残留预览，再装 v2 并确认旧预览。
   核对 v1 仍报告已卸载，清理被拒绝，快捷方式保持原位。
   在独立快照复测生成预览前的边界。在 v1 卸载完成核实后、残留扫描前暂停，装好 v2 后继续。
   核对 v1 的卸载结果仍可见，快捷方式保持原位，且没有可执行的残留预览。
2. 使用卸载时移除自身 HKCU 卸载键的 Win32 样本，保留专属目录内的标记文件和可清理的 HKCU 设置值。
   取得残留预览后分别复测恢复原键、创建不同键但指向同一旧安装目录的登记。
   确认旧预览，核对前一种情况阻止清理，后一种情况保留重叠目录内的标记文件。
3. 在独立快照中复测逐项写入前的边界，每次只勾选一项。
   文件用例在隔离意图写入后、逐项复核前暂停，注册表用例在打开写事务的逐项复核前暂停。
   从同一账号恢复原 HKCU 卸载键后继续，分别核对文件和注册表值保持原样，该项没有清理成功回执。
4. 准备可正常卸载且留有测试文件和可清理注册表值的 MSI 样本。
   分别在原生成功结果返回后、首次扫描前，以及取得预览后、确认前暂停，保持原 ARP 键缺失。
   在独立快照或受控查询夹具中，分别让机器级、当前用户托管、当前用户非托管上下文返回同码产品已安装或已公告，也模拟任一上下文查询失败。
   核对首次扫描被阻断，或旧计划无法执行，测试文件和注册表值保持原样。
5. 在每个目标的备份意图写入后、逐项 MSI 复核前重复用例，每次只确认一个文件或一个可清理的注册表值。
   核对文件保持原位，注册表测试值保留，失败项无成功回执。
   另用其他管理员账户批准提权助手的机器级卸载，让同码产品仅在普通桌面账户的每用户上下文出现，再继续首次扫描。
   核对桌面端仍会阻止残留清理，即使助手账户下的核验已通过且机器级 ARP 键已经消失。

## ARP 目录归属

Win32 卸载的登记目录和推断目录、卸载后的独占目录、按名称匹配的文件系统候选以及便携目录检查，使用同一套 ARP 路径证据。
每轮操作单独读取一次这组证据，执行前复核时重新读取。
路径证据独立于应用列表，因此隐藏或没有 `DisplayName` 的登记也会参与归属检查。

`InstallLocation` 提供目录证据。
`DisplayIcon`、`UninstallString` 和 `QuietUninstallString` 的字面路径只提供所引用文件的证据。
检查同时使用登记中的字面路径，以及可在不跟随链接的情况下核实的规范路径。
如果含糊的原始值仍能明确指向被检查目录下的路径，也会阻止相关操作。
读取登记失败时，受影响的清理项无法执行。
有归属重叠时，按名称匹配的候选保持只读，对应的独占目录扫描则跳过。
归属判断以可核实的登记证据为限。

1. 准备一个应用名与专属安装目录名匹配的当前用户 Win32 样本，保留一个带启动标记的测试卸载器。
   创建第二个没有 `DisplayName` 的 HKCU 卸载登记，使其 `InstallLocation` 与样本目录重叠。
   确认第二条登记未出现在应用列表，且样本的卸载预览报告归属冲突，未生成启动标记。
2. 从独立快照复测第二条登记也省略 `InstallLocation` 的情况。
   分别只设置 `DisplayIcon`、`UninstallString` 或 `QuietUninstallString`，使引用文件位于样本目录内。
   对不含归属冲突的便携夹具先生成正常预览，再用同样的无名登记指向其内部文件，确认该目录不能用于便携清理。
   用只在同级目录中带相同名称前缀的路径作对照，确认对照不阻止原样本。
   在启用 8.3 短文件名的卷上，用实际短名引用样本目录内的现有文件，核对规范路径仍能识别冲突。
3. 从无冲突状态执行官方卸载，让测试卸载器留下文件标记，保留清理预览。
   随后创建不同键名的重叠登记，保持原卸载键缺失，再确认旧预览。
   核对复扫阻止移动冲突文件，相关标记保持原位。
   在独立快照中于核实官方卸载后、自动扫描前暂停并添加重叠登记。
   继续后核对名称候选只读或独占目录不再被扫描。

## 原安装目录身份

启动官方卸载器前，记录符合条件的 `InstallLocation` 及整条祖先目录链的卷标识、文件 ID 和创建时间。
采集通过不跟随链接的目录句柄完成，句柄在启动卸载器前释放。[Microsoft FILE_ID_INFO 说明](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)
生成清理预览、确认后复扫和每项写入前都核对原目录身份。
若发现原目录或祖先被替换，已核实的官方卸载仍显示完成，残留清理停止。
确认路径缺失时，只有原受信根和所有仍存在的祖先目录身份一致，才能接受正常移除。
目录的修改时间变化本身不影响身份核对。

缺少可用的登记位置或卸载前证据时，清理资格须由独立的归属证据建立，与仍可辨识的登记路径重叠的候选保持只读。
快捷方式等引用旧目录的条目在解析目标时，把仍可到达的祖先目录与原证据逐一核对。
文件隔离使用绑定全部祖先目录身份的指纹，并通过保留的句柄执行重命名。

1. 准备只移除自身登记并保留测试文件的 Win32 卸载器。
   在测试卸载过程中、原目录文件句柄释放后，将样本安装目录移至另一位置，在原路径新建目录并放入同名标记文件。
   核对原卸载仍显示完成，且没有可执行的残留预览。
   另用独立快照在取得预览后执行同样替换，再确认旧预览，核对新目录内的标记保留。
   逐项写入前的反例可在写入隔离意图后、逐项复核前暂停，再替换目录。
2. 在专用快照中以 `旧目录\外层\内层\标记文件` 为隔离候选。
   在通过逐项复核后、隔离打开源文件前暂停，原地替换 `外层`，把原来的 `内层` 整体移入新外层。
   保持标记文件及其直接父目录身份，继续后确认隔离仍因祖先链变化而被拒绝。
3. 用正常删除原目录的样本复测，保留受信根和仍存在的祖先目录。
   核对旧目录的正常缺失通过身份复核，并按失效快捷方式的条件验证留下的 `.lnk`。
   另复测原目录仍在但卸载器写入测试标记而改变目录修改时间的情况，核对合格残留仍可预览。

## 文件还原中断

1. 在专用 VM 中隔离同卷 NTFS 上的一个测试文件，记录原位置和隔离槽。
   确认还原后，在调试器中于同卷重命名成功、写入还原回执前终止进程。
2. 重启应用并打开隔离区。
   核对经验证的隔离目录中原槽位已空，原位置的文件、父目录身份和相关文件指纹与备份一致。
   应显示「已还原」，并补记该备份的还原回执。
3. 在独立的测试快照中复测原文件缺失、原位置被不同文件占用，以及原槽位被不同对象占用。
   这些反例应保持「需要复核」，保留现场，且还原回执应保持缺失。

文件和父目录身份使用 NTFS 卷标识与文件 ID 核对。同卷限制仍适用。[Microsoft FILE_ID_INFO 说明](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)

## 当前用户的多级应用设置

经核实的 Win32 或 MSI 官方卸载完成后，或符合条件的 Win32 强制移除预览中，工具可检查 `HKCU\Software\发行商\应用` 下的多级设置。
发行商和应用名须与选中登记精确对应。
原生 HKCU 视图按桌面进程的用户 SID 打开，用户 hive 必须已加载。机器级设置继续只读。[Microsoft 预定义注册表键](https://learn.microsoft.com/en-us/windows/win32/sysinfo/predefined-keys)

从应用根键向下最多检查三层，每个应用的枚举限额为 128 个子键和 512 个值。
扫描超限时提示未能完成，未完整枚举的键及超出深度的对象无清理权限。
候选仅限可原样备份的具名值，风险为高，需手动勾选。
整键、默认值、注册表符号链接和受保护分支均排除，受保护分支包括 `Policies`、`Shared` 和存放许可证的 `Licensing`。
另一应用与根键或子键名称冲突，且发行商匹配或未知时，该分支退出清理范围。

预览、确认复扫与逐项备份写入后均重新读取 ARP 卸载登记来核对归属。
实际变更前先保存 `.reg`、类型快照和备份清单，再执行逐项复核，通过后才可在事务中移除选中的值并提交凭证。
最终 ARP 复核与设置写入独立执行，外部登记仍可能在两步之间变化。
还原要求目标键仍存在、类及安全描述符匹配，且目标值名尚未被占用。
匹配依据为精确地址、权限和保存的值数据。
这组证据无法区分同路径、同类且权限相同的重建键。[Microsoft 注册表键属性](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw)

1. 在普通账号 VM 为 `Norvale Studio` 的无害 Win32 样本 `Aurora Draft` 准备测试登记。
   在 `HKCU\Software\Norvale Studio\Aurora Draft\Settings\Preferences\Current` 添加两个 `REG_DWORD` 值 `Enabled=1` 和 `Keep=2`，另设一个有标记的子键。
   让样本卸载器移除自身的 ARP 键并保留设置。
   分别用成功的 MSI 样本和确实缺少卸载器的合格强制移除样本复测。
2. 打开残留清单，核对具名值为高风险且默认未勾选。
   手动只选 `Enabled`，确认 `.reg`、原始类型快照及备份清单在删除前生成，且 `.reg` 和快照都只备份该值。
   对照审计和事务凭证，确认删除发生在逐项复核之后。
   隔离区还原后核对 `Enabled` 的原始类型和内容，并确认 `Keep`、对照子键及其内容始终保留。
3. 单独复测默认值、整个 `Current` 键、第四层具名值、HKLM 对照键及 `Shared`、`Policies`、`Licensing` 分支。
   另用专用夹具创建一条指向无害对照键的原生注册表符号链接。
   核对这些对象无可写候选，链接目标保持原样。[Microsoft 注册表链接打开选项](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw)
4. 分别在独立快照中为应用根键准备 129 个直接子键，或给一个无害设置子键添加 513 个具名值。
   核对触发枚举提示，超限键的内容无法确认清理。
5. 在首次预览前、确认复扫前，以及备份已写入但最后一次 ARP 复核尚未开始时，分别加一个不同 ARP 键的同名软件登记。
   依次使用匹配和缺失 `Publisher` 的冲突登记，并复测同发行商软件名与某个子键名冲突的情况。
   核对受影响的值留在原位，逐项复核拒绝时已写入的备份仍保留，且没有该值的清理成功凭证。

   每种情况均应拒绝还原，且保留原备份和现有对照内容。

## 注册表提交后的中断恢复

注册表清理仍在删除前保存 `.reg` 和带原始类型的快照。
删除及还原各自通过同一注册表事务提交目标变更和本机提交凭证。 [Microsoft 注册表事务](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeytransactedw) · [Microsoft CommitTransaction](https://learn.microsoft.com/en-us/windows/win32/api/ktmw32/nf-ktmw32-committransaction)
凭证位于当前用户受保护的非易失性键 `HKCU\Software\UninstallAny.RegistryRecovery`，由 34 字节记录绑定备份 UUID、精确注册表目标、带类型的快照摘要及操作阶段。

进程中断后，隔离区用本机凭证核对状态，读取期间保持注册表和原有文件回执原样。
清理凭证通过核验时，即使缺少清理完成回执，也可重新预览并确认正常还原。
还原凭证通过核验后，即使目标后来再次消失，同一备份也无法再次还原。
目标键或值的现存状态只供对照，判定以可核验的凭证和备份为依据。
凭证、回执或快照损坏或无法核实时，保留备份供复核。
本节验收范围为桌面进程终止后的恢复。

1. 在普通账号的专用 VM 中准备一个可写的 HKCU 测试键或单值，以及同键或同级的无关对照项。
   确认清理，在调试器中于备份写入后、调用 `CommitTransaction` 前终止进程。
   重启后核对原目标和对照项仍在，备份保留，没有可用的提交凭证，且隔离区无法把该项作为已清理备份还原。
2. 换用独立快照，于清理事务成功提交后、写入 `Applied` 文件回执前终止进程。
   重启并读取隔离区，核对测试目标已移除、本机凭证可核验、缺失的文件回执仍保持原状。
   核对该备份可进入正常还原预览，确认时只恢复测试项，对照项保持原样。
3. 另行清理测试项以生成新的备份，在还原事务成功提交后、写入 `Restored` 文件回执前终止进程。
   重启后核对原对象已恢复、隔离区显示「已还原」，结果来自本机还原凭证。
   从专用夹具中再次移除该测试项，复查同一备份仍无法再次还原。
4. 在独立快照中，于确认还原前用另一份测试值占用原位置。
   核对还原中止、占位值保持原样、没有还原提交凭证。
   移除测试占位值后重新预览并确认，核对原备份仍可正常还原。
5. 选取早期版本留下的有效备份，核对使用既有文件回执即可确认还原。
   在各自独立的专用快照中，分别损坏本机凭证、替换另一测试备份的凭证，以及改写原始类型快照。
   对缺少文件回执的样本，核对冲突或损坏的证据阻止状态判定及还原，且对照项保持原样。

## 到期目录链接

隔离默认保留 14 天，用户可为新备份调整保留期。
到期后仍须先审阅清单，再逐项勾选并确认永久清理。
清单只包含已有成功隔离回执 `Applied`、当前可验证同卷私有槽位、对象身份和访问控制的备份。
这包括此前已隔离的受支持目录符号链接及已验证的直接本地目录联接。
普通目录、卷挂载点、其他重解析对象以及标为只读的槽位对象都排除在到期清单之外，原只读属性保留。

清理通过不跟随重解析点的槽位句柄提交 `FileDispositionInfo`。
关闭句柄后核实该槽位已不存在，才记录永久清理完成。
链接目标及内容保留，隔离后出现在原路径的新对象同样保留。
若槽位消失但缺少永久清理回执，状态保持「需要复核」。[Microsoft NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) · [Microsoft FileDispositionInformation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information)

1. 在同卷 NTFS 的专用 VM 中准备带标记文件的非空普通目录，并在另一测试目录中创建指向它的目录联接。
   另以目录符号链接复测，创建夹具时若系统要求，可在专用 VM 启用开发者模式。
   通过清理预览仅隔离链接本身，确认目标目录和标记保留。
2. 在链接的原位置创建新的普通测试文件，待隔离备份到期后，核对链接槽位可审阅且默认不勾选。
   确认永久清理后，核对槽位消失且产生回执，目标目录、目标标记和原位置的新文件均保持原样。
   用普通目录作为对照，确认它无法进入永久清理清单。
3. 用独立夹具复测只读隔离文件，确认它不出现在到期清单中，只读属性仍在。
   另在生成到期清单后换掉一个已审阅槽位，或用另一个进程占用已审阅的普通文件槽位并禁止共享删除。
   确认旧清单拒绝清理相应项，替换对象和被锁文件均保留。
4. 在专用快照中于槽位消失后、写入永久清理回执前终止进程。
   重启后该备份应显示「需要复核」，目标和原位置的新文件仍保留。

## 缺少 InstallLocation 的 Win32 卸载

此路径只用于当前用户的 HKCU Win32 登记，且 `InstallLocation` 值必须确实不存在。
`UninstallString` 须直接指向无参数的本地卸载 EXE，`DisplayIcon` 须为指向本地 EXE 的字面 `REG_SZ`，可以附带数字图标索引。
两个 EXE 必须是不同的普通原生程序，位于同一个与应用名严格匹配的目录。
该目录必须是当前用户默认本地 `FOLDERID_UserProgramFiles` 的直接子目录。[Microsoft 已知文件夹标识](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid) · [Inno Setup 卸载图标说明](https://jrsoftware.org/inno-setup/documentation/topic_setup_uninstalldisplayicon.htm)

归属检查也会读取其他卸载登记中没有 `DisplayName` 的键。
启动前重新读取登记并核对两个 EXE 的身份与文件哈希。
卸载使用交互模式，推断目录仅用于限定本次启动，应用列表的安装位置仍为空，残留扫描也不会凭该推断遍历目录。

1. 在普通用户 VM 中，在默认的 `%LOCALAPPDATA%\Programs` 下创建 `Scope Sample` 目录。
   将经批准的本地无害测试 EXE 普通复制到该目录，分别命名为 `Uninstall.exe` 和 `Sample.exe`。
   让测试卸载器在启动时写入标记，随后仅移除它自己的测试卸载键，并正常退出。
   在同一用户的 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall` 下创建独立样本键，设置 `DisplayName` 为 `Scope Sample`。
   把 `UninstallString` 写成带引号的 `Uninstall.exe` 绝对路径，`DisplayIcon` 写成 `Sample.exe` 的字面 `REG_SZ` 绝对路径，可加 `,0`，省略 `InstallLocation`。
2. 预览并确认该样本，核对安装位置留空、卸载方式显示为交互模式、启动标记写入且样本登记已移除。
   使用另一个留在样本目录内的普通标记文件，核对该目录内的文件不会仅凭推断范围出现在残留清单中。
3. 从独立快照分别复测空的 `InstallLocation`、错误类型或格式的登记值、带参数的卸载命令及硬链接或重解析点夹具。
   再创建一个指向样本目录的无名卸载登记，核对归属冲突同样阻止启动。
   另在打开预览后修改 `DisplayIcon`，或以另一份合格测试 EXE 内容改写其中一份程序，再确认原预览。
   各反例均应保留样本登记和测试文件，且不出现卸载器启动标记。

## MSI 提权助手

受支持的路径仅覆盖机器级 MSI。
普通卸载明确报告权限不足时，桌面端可请求 Windows 管理员确认。助手会从本机安装记录读取产品名称与 ProductCode，并单独确认本次操作。
普通卸载失败且原因无法确定时，桌面端保留原始结果。
系统组件、禁卸载登记、来源不一致的 MSI 和当前提升令牌下存在的同码每用户 MSI 都不能进入该路径。
[Windows Installer 安装上下文](https://learn.microsoft.com/en-us/windows/win32/msi/determining-installation-context)

助手二进制 `uninstallany-helper` 由 `privileged-helper` 构建特性启用。
助手只从经核实的每机安装目录接受请求。便携 ZIP 和普通开发产物使用普通卸载路径。

助手为单次请求建立本地管道，验证活动的桌面进程和 Windows 会话后才读请求。
请求仅携带受支持的 MSI 产品身份、范围和预览指纹。
提升后要求在默认拒绝的确认框中核对产品，开始执行前再次读取登记。
请求发送与结果丢失的验收见[跨实例写入保护](#跨实例写入保护)。
助手成功返回后，桌面账户仍执行[卸载后重新出现](#卸载后重新出现)中的 MSI ProductCode 核验。

### Windows x64 MSI 预览安装包

准备 Python 3.11 或更新版本、msitools 的 `wixl`、`msibuild`、`msiinfo` 和 `msiextract`。
打包输入为已构建的 x64 桌面程序、启用助手特性的 x64 助手和匹配的 `WebView2Loader.dll`。
在仓库根目录使用本地输入构建未签名 MSI，产物仅供专用 Windows VM 验收。

```sh
python3 scripts/package_windows_installer.py \
  --gui /path/to/uninstallany-desktop.exe \
  --helper /path/to/uninstallany-helper.exe \
  --loader /path/to/WebView2Loader.dll \
  --tools-dir /path/to/msitools/bin \
  --output-dir target/dist/windows-msi-preview \
  --unsigned-preview
```

MSI 使用 Windows Installer 标准表把 `UninstallAny.exe`、`UninstallAnyHelper.exe` 和 `WebView2Loader.dll` 安装到固定的 `ProgramFiles64Folder\UninstallAny`。
安装目录及三个文件使用显式 ACL，内置 Administrators 是所有者，`SYSTEM` 和 Administrators 有完全控制权限，普通 Users 只有读取和执行权限。
安装器以管理员权限完成每机安装。安装完成后，以普通权限直接启动安装目录中的 `UninstallAny.exe`。
安装包没有自定义操作和安装后自动启动步骤。[Microsoft MsiLockPermissionsEx](https://learn.microsoft.com/en-us/windows/win32/msi/msilockpermissionsex-table)

打包、安装与应用功能均使用本地数据。目标系统须已提供 x64 WebView2 Runtime，包内的 `WebView2Loader.dll` 负责加载该运行时。
在缺少运行时的离线系统上，管理员可从单独准备的 Microsoft Evergreen 独立安装程序部署运行时，再启动桌面端。[Microsoft WebView2 运行时分发](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution#offline-deployment)

公开发行须对桌面程序、助手和最终 MSI 做 Authenticode 签名并核验，签名环节独立于本地未签名预览打包。[Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)
原生 Windows 构建、实际安装与卸载，以及助手 UAC 行为仍待实机验收。
更新的预览包沿用产品标识和版本号，按干净快照验收。
如果测试机已经安装同版本预览，先关闭程序并从 Windows「设置 → 应用」卸载，再安装更新的预览包。

### Windows VM 验收

1. 在安装了 WebView2 Runtime 的 Windows 10/11 x64 快照上断网安装预览 MSI。
   核对安装只写入固定的 64 位 Program Files 应用目录，三个文件名与上文一致，安装完成时没有桌面或助手进程自动启动。
   用 `Get-Acl` 或 `icacls` 检查目录和三个文件的所有者与权限，并用普通用户尝试改写、改名和替换文件，核对写入均被拒绝。
2. 以普通用户手动启动已安装的 `UninstallAny.exe`，核对 GUI 无 UAC 提示，应用清单正常加载。
   选择一个需要管理员权限、符合助手路径的第三方机器级测试 MSI，从普通权限 GUI 发起卸载。
   在不同快照分别拒绝 UAC、通过 UAC 后拒绝助手产品确认，以及用另一管理员账户依次通过两次确认。
   核对助手展示所选名称和 ProductCode，拒绝时保留应用，批准时仅处理所选产品。
3. 在 Windows Installer 或卸载登记中核对 UninstallAny 自身机器级安装的 ProductCode 为 `{B82A69F2-4229-4428-ADF3-001FBCFB2C16}`。
   核对该产品在 GUI 中按受保护项处理，不能从应用内执行卸载、强制移除或助手请求。
   用产品名相同、ProductCode 不同且安装路径独立的无害 MSI 作对照，核对名称本身不会触发自身保护。
4. 在隔离区保留一个可还原的无害备份，并记录当前用户的设置和日志等数据。
   关闭 GUI，从 Windows「设置 → 应用」卸载 UninstallAny，核对本机产品登记和 MSI 管理的三个文件被移除，`%LOCALAPPDATA%\UninstallAny` 下的用户数据仍在。
5. 在确实缺少 WebView2 Runtime 的独立快照中保持断网并复测 MSI 安装。
   核对安装器没有发起运行时下载，GUI 在部署运行时前无法使用。
   使用预先准备的官方离线运行时安装程序后再次断网启动，核对 GUI 可以加载。
